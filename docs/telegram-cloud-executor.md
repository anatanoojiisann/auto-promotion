# Telegram 专用云端执行器

`cloudflare/telegram-executor` 直接运行在 Cloudflare Workers，使用固定版本 teleproto 1.230.1 和 Node 兼容运行时，不依赖 Python 容器。仓库配置关闭 workers.dev 且不设置公开路由，通过现有控制服务的私有服务绑定访问。

## 配置与验证

控制服务的 `TELEGRAM_EXECUTOR_ACCOUNT` 与执行器的 `TG_ACCOUNT_ID` 必须对应同一账号，两个服务的绑定名称分别为 `TELEGRAM_EXECUTOR`、`CONTROL_INTERNAL`。执行器通过 Worker Secrets 配置 `TG_API_ID`、`TG_API_HASH`、`TG_EXPECTED_ID` 和十六进制 AES 密钥 `TG_SESSION_KEK`；两个服务还需配置相同、独立于操作员令牌的 `TG_QUEUE_BRIDGE`。凭据和会话不能写入仓库。

切换账号时保留原任务和历史结果，创建新的冻结任务。将该账号已有的读写冷却截止时间以 Unix 秒写入 `TG_ACCOUNT_NOT_BEFORE`；执行器取配置时间与持久化读写冷却时间的较大值，在创建读写连接前拒绝采集和提交。无效冷却配置也拒绝读写；状态查询仍可用。独立设备授权不受旧读写冷却连带阻止；若登录接口自身返回限流，则持久化 `login_cooldown_until` 并阻止再次发起登录，轮询仍只读。更换账号的 Durable Object 不继承旧账号会话，需要本人完成独立登录。

先安装 `cloudflare/control-plane` 的依赖，再在本目录运行 `npm ci`、`npm test` 和 `npm run check`。最后一项仅打包，不部署。修改绑定及凭据后仍须独立部署、本人登录和实际环境验收；提交源码与测试通过不代表这些步骤已完成。

## 已补充

- Telegram 应用连接配置保存在 Worker Secrets。创建独立云端登录，不复制 Windows 会话。新会话使用 AES-GCM 加密后保存到专用 Durable Object；加密密钥不进入业务快照。
- 独立设备二维码登录及账号身份核对。只有匹配本轮指定身份、非机器人且未受限的会话可以读取或执行。
- 登录后的搜索、简介/置顶/近期消息、原消息与回复上下文、成员身份和消息回执读取。仅支持公开讨论入口；不读取联系人私聊，不按成员名单私信。
- 加入公开讨论群、带原消息上下文的纯文本回复适配代码。平台写操作必须对应原生冻结任务、有效租约、唯一尝试和队列授权。
- 写入前再次检查停止状态、账号归属、配额、审核、原消息和新回复。未知结果只读核对；换任务 ID 不能重复入群。同一账号串行。
- 队列和执行器用单独的 HMAC 密钥认证。原操作员密钥不变；Windows 的旧绑定和其他账号的通道不变。
- 登录后可启用受保护的采集调度；历史入群尝试增加独立的只读核对步骤，不重发。云端账号归属启用接口需要健康核验和无有效写入租约。
- `/v1/workflow/state` 支持按活动暂停/继续/取消，不改动全局停止、冻结定义或历史结果。
- 已完成独立授权但旧读写限流尚未结束时，可登记延迟启动。服务器仅核对已保存的身份与会话恢复证明，不提前调用 Telegram 读写接口；到期后由现有定时调度重新验证健康、账号占用和通道归属，再自动启用采集与派发。其他待执行活动占用同一账号、全局停止、活动暂停和新增限流都会继续阻止启用。

## 控制接口

状态：`POST /v1/executor/telegram/status`。其余配置请求均须使用现有操作员令牌和绑定数据库的签名。

- `login-begin` / `login-poll`：独立设备授权。二维码令牌不写入普通审阅日志；需要手机本人确认。如果 Telegram 要求两步验证，必须使用保护的认证流程，不能在聊天中收集密码。
- `read`：只允许白名单读取动作，不能传入 execute/join 绕过队列。
- `start-reader` / `stop-reader`：启停已登录的采集任务；不会直接发布。
- `activate`：身份核验后将本轮指定账号交给真实云端节点。不会解除停止、提高额度或重试未知结果。
- `link-native`：只连接已经准备且显式启动的原生任务；检查研究/互动资格、原文、回复目标、会员身份和冻结版本。
- `dispatch-native`：只消费上述连接，原生队列仍负责租约、限额、时间窗和一次性尝试。
- `gate`：独立 HMAC 验证的执行前授权；普通操作员/节点请求也不能用未签名调用绕过。

## 已准备正文的完整业务流程

`telegram-prepared-replies.mjs` 和 `telegram-task-builder.mjs` 已接通精确正文流程：由操作者准备目标群、原消息、完整回复和审阅证据，服务器保存正文，执行研究/机会/草稿/发布前校验，再生成冻结的入群或发送子任务，交给现有原生队列。此流程不需要模型服务，不会自行改写回复。接口和用法见 [准备内容后线上发布](prepared-telegram-replies.md)。

语义判断由准备内容的操作者完成并提供原文引用；服务器核验引用、当前规则和上下文的一致性，不能将布尔断言或公开网页摘要当成认证聊天证据。正式子任务继承原任务的账号、目标边界、时间窗、额度和冷却；同一目标/原消息不能靠新建任务重复提交。未知结果不重发。实际问题、群规和上下文不足时保持等待，不能用模板广告填满数量。

产品推荐、链接和演示需要对应的安装版本及验收证据；缺失时不会通过产品回复审核，但仍可准备采集及普通答疑。真实群内发送验收须等符合全部条件的机会。

论坛主题规则、规则外链和超过当前采样范围的完整读取还需扩展；这些情况不会自动判定群规已核实。当前未开放独立公告、附件/录屏演示或私信投递。原生写入归属启用时会检查同账号的其他待办，不能抢占其他批次。

部署后的独立登录仍需本人完成。仅有 API 配置、二维码、单元测试或已注册节点，都不构成已完成登录、入群或发言的证据。通过控制接口读取登录和队列状态，并以独立平台回执核对实际结果。
