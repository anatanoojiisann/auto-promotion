# 社交平台三小时播报

## 当前播报规则

北京时间每三小时发送一条汇总，固定在 00:00、03:00、06:00、09:00、12:00、15:00、18:00、21:00。每个窗口只生成一个稳定通知编号，七个平台合并到同一条消息中。30 秒轮询只用于读取数据，不代表每 30 秒推送。

消息正文包含各平台的发送、成功、失败和当前“队列中”数量，TikTok 保留“私信互动”一项。不附标题、时间、任务详情、账号状态、其他反馈指标或通知编号。没有已确认结果或没有待执行项目时，对应数量显示 0；尚无私信核验数据时，TikTok 私信项显示“未接入”，不以 0 替代未知。

```text
Telegram：发送 30 条｜成功 28 条｜失败 2 条｜队列中 8 条

X：发送 20 条｜成功 19 条｜失败 1 条｜队列中 5 条

Reddit：发送 0 条｜成功 0 条｜失败 0 条｜队列中 0 条

Instagram：发送 0 条｜成功 0 条｜失败 0 条｜队列中 0 条

Facebook：发送 0 条｜成功 0 条｜失败 0 条｜队列中 0 条

Discord：发送 0 条｜成功 0 条｜失败 0 条｜队列中 0 条

TikTok：发送 0 条｜成功 0 条｜失败 0 条｜私信互动 未接入｜队列中 0 条
```

上面的数字仅用于说明格式。

任务启动、任务结束、进度里程碑、账号异常或恢复、全局停止变化、服务启动、20:00 累计、00:05 日报以及历史报表更正，均不自动推送到本通道。原业务记录与历史通知审计保留。

## 数量口径

汇总上一个三小时内确认的真实投递结果：发送数等于成功数加明确失败数。成功必须具有 `confirmed` 状态、`verified=true` 和真实外部引用；以核验记录的时间归属窗口。失败必须有明确的 `failed_known` 结果与实际执行记录，以该执行记录确认结果的时间归属窗口。

未知、处理中、尚未实际发布的排程、未尝试、错过、取消和模拟项目均不冒充成功或明确失败。迟到回执确认后计入随后窗口，不补发旧窗口。单纯点赞、入群、隐藏和删除等管理操作不计入“发送条数”。

这些是本期明确结果的运营汇总，不按计划发送时间推算实际发布，也不表示未决项目已经失败。

“队列中”是读取时刻的待发送条目数，不是任务批次数，也不限定于刚结束的三小时。它直接读取 `execution_jobs` 的真实发送队列：任务已激活且清单就绪，队列状态为 `pending` 或 `leased`，条目仍为 `not_attempted` 且没有历史尝试记录，队列尚未过期。已排队但等待计划时间、冷却或额度的条目仍计入；领取后尚未尝试提交的项目也计入。

草稿、暂停、取消、已完成、过期、正在提交、结果未知、待人工登记和平台已接受的排程均不计入待发送数；模拟项目、入群、点赞及管理操作不计入。相同投递项只计一次。队列查询使用当前读取时间，而非历史报表的截止时间，且不会更改任务队列。队列变化本身不会追加通知，仍等待下一次三小时播报。

2026-10-27 修正 TikTok 排期互动的队列取数。该批计划按既定间隔逐条创建正式任务，因此尚未到期的已授权条目不会出现在 `execution_jobs` 中。通知服务现在同时读取显式登记的运行中计划，按会话和原消息标识与正式任务去重；正式回执优先于计划文件的旧状态，已发送、已尝试、结果未知、已停止的条目不再算待发送。

计划只用于只读数量投影，不会被通知服务执行或导入发送器。仅处理本机 `var/private/` 内显式登记的 TikTok 私信计划，要求执行授权仍有效、对应 heartbeat 为 ACTIVE、账号与批次绑定匹配、已审核清单哈希一致。已获用户接受授权且等待处理的消息请求计入计划队列；接受结果不明时排除。计划读取或核验失败时显示“队列中 未统计”，不将故障伪装成 0。私信内容、对方信息和计划全文均不进入播报或通知日志。

新增批次可用以下命令登记为通知数据源；该命令不启动、重排或发送任务：

```powershell
.\.venv\Scripts\python.exe -m auto_promotion.alert_service --plan-file var/private/example/reply-plan.json register-queue
```

来源登记持久保存在通知库 `alert_meta.planned_queue_sources`，无需修改计划文件。状态中的 `queue_sources` 展示各来源是否有效和计划队列数量；`runtime.summary_format=platform_counts_planned_queue_v2` 表示常驻进程已加载本次修正。新增数量仍只随原有三小时播报发送，不追加旧报表更正或私信通知。

2026-10-26 按用户要求增加 TikTok 私信互动数，按本窗口内已核验并登记的外发私信消息条数统计，包含私信发送和私信回复，不按人数／会话数统计，也不包含收到的消息或未读角标。明确失败、未知和模拟私信不计入该项。它是成功发送数中私信部分的细分，不额外加到总发送数。

结果记录必须明确标记私信：动作 `direct_message`、`send_direct_message`、`reply_direct_message`，或动作 `send_message`／`send_file`／`reply` 且 `interaction_channel='direct_message'`。普通 `comment`／`reply` 和收件人 ID 不会被推测为私信。此处只定义统计凭据，不新增或启用私信发送能力。

TikTok 网页私信采集与任务回执通道见 [私信接入说明](tiktok-private-messages.md)。尚未采集过真实收件箱、也没有可靠私信结果的账号，显示“私信互动 未接入”。采集通道在统计截止时间前完成身份核验并接入，或已存在可靠私信结果后，按同一三小时核验窗口显示已登记数量；若该窗口没有新核验的私信，显示“私信互动 0 条”。导入的历史收件箱消息不算新发送。这不是 TikTok 收件箱全部活动的统计，未登记的人工私信不可推算。

## 去重和恢复

- 通知唯一键只使用三小时截止时间，不包含报表版本或内容哈希。相同窗口的数据改变不产生第二条消息。
- 新安装、规则升级、正常重启均不发送启动摘要，也不逐条补发过去的窗口。
- 待机或断线恢复后，只补最近一个尚未提交的三小时窗口；不会逐条补发更早的窗口。每个窗口仍使用同一个唯一编号，只能提交一次有效通知。
- 最近窗口在下一个三小时整点到来前保持有效，超过五分钟不再直接丢弃。下一个整点到来后，旧的未发送通知过期，只处理新窗口。
- 明确拒绝可在当前窗口内有限重试；提交结果未知时保留原记录，不重新创建或重发。
- 发送领取环节另设白名单，自动发送仅允许当前窗口的 `platform_summary`；旧任务、恢复和历史报表消息无法混入发送队列。
- 密钥、请求响应正文和社交平台凭据不进入消息或通知审计。

通知服务读取业务库时强制使用 SQLite 只读连接，通知队列与游标单独保存在 `var/alerts.db`。它不启动社交任务、不改变额度、冷却或全局停止状态。

## 运行和状态

Windows 服务名为 `AutoPromotion-Alerts`，登录后启动，失败后自动恢复。当前服务引用用户提供的私密密钥文件；移动该文件后需同步更新服务配置。

`AutoPromotion-Alerts-Boundary` 在北京时间每个三小时整点请求系统唤醒，并运行一次采集与发送周期。它复用主服务的私密文件引用和同一通知数据库，不读取或复制密钥。主服务和整点周期即使同时运行，也只能领取同一时段的一条通知。整点任务不会在安装时立即运行；原主服务的五分钟存活检查不启用唤醒，以免每五分钟打断待机。

已有安装可运行 `scripts/install-alert-boundary-wake.ps1` 增加整点唤醒任务。此任务使用当前已登录用户，不改变系统整体睡眠策略。系统不允许唤醒、机器关机或网络不可用时，仍不能保证准时送达；恢复后只补最新窗口，避免历史通知洪泛。状态接口的 `summary_recovery_policy=latest_only_until_next_boundary` 表示恢复规则已加载，迟到恢复信息记录在 `last_recovered_summary`。

从项目根目录执行：

```powershell
# 预览当前统计窗口的简洁正文，不发送
.\.venv\Scripts\python.exe -m auto_promotion.alert_service preview
# 查看服务心跳、推送规则、下次播报时间与队列状态
.\.venv\Scripts\python.exe -m auto_promotion.alert_service status
# 新环境安装；不覆盖已有同名服务
.\scripts\install-alert-service.ps1 -KeyFile C:/private/.env
```

`GET /api/alerts/status` 沿用工作台身份验证，业务进程下次启动后加载。状态中的 `delivery_policy=three_hour_counts_v1` 表示新规则已启用，`next_summary_at` 为下一次北京时间三小时边界的时间戳。

`test` 子命令仍保留供明确要求的人工联调用，自动服务不会调用它。HTTP 2xx 记录为接口已接收，接收端最终送达不作无依据的承诺。

## 频率问题修复记录

2026 年 10 月 25 日的通知记录显示，14:00 后共提交了 20 条消息，其中 17 条集中于 17:34 的历史报表补发。旧实现对每份历史报表分别检查内容变化，晚到回执导致多份旧报表变化，因而集中生成更正通知；同时还启用了独立的任务进度推送。

当前实现改由 `alert_summary.py` 直接读取本期已确认结果，不再把保存报表及其修订作为外部通知触发器。服务升级时淘汰待发送的旧规则消息，并保留已经提交的审计记录。验收覆盖历史报表成批变化、重启、断线、午夜、20:00、未知结果和并发领取，确保不会再次按旧报表数量放大推送。

2026 年 10 月 27 日 09:00 没有生成通知。系统电源事件显示电脑在 08:58:59 进入待机，09:36:54 恢复；旧规则超过五分钟会前移游标但不创建通知。当天 06:00 的通知已由接口接收。修复增加独立整点唤醒任务，随后将迟到规则改成“恢复后只补最新漏播一条，下一整点淘汰更早窗口”。已被旧规则跳过的历史游标不回滚，因此规则升级本身不会触发旧消息补发。
