# 完整活动的线上队列

`workflow-queue.mjs` 在现有 Cloudflare Durable Object 内保存独立的活动主任务、冻结定义、工作步骤、依赖、租约和结果。原有平台尝试表、账号通道、配额、全局停止和未知结果保持不变。

主任务覆盖发现入口、读取群规和近期消息、研究判定、互动机会判定、成员核验、入群计划、回复草拟、发布前审核、发送计划、回执核验和后续答疑。搜索成功后将新入口去重并展开为完整步骤，同时保留下一轮搜索时间。没有适配问题时应提交 `defer` 并注明原因，不能伪造互动资格或将目标标为完成。只有独立讨论入口的已确认合格互动回执达到目标数，目标检查才会通过。

控制接口：

- `POST /v1/workflow/create`：操作员签名的显式启动，按定义哈希幂等；修改冻结定义必须新建主任务。
- `POST /v1/workflow/status`：按阶段汇总及分页步骤。区分等待云端节点、依赖、时间、原生动作派发、全局停止、执行中和已核对结果。
- `POST /v1/workflow/node`：注册独立的云端编排节点。原 Windows 节点不能消费此队列；这里不能注册 join/send 能力，也不会授权平台写操作。
- `POST /v1/workflow/claim`、`POST /v1/workflow/result`：云端节点领取只读/评估工作，180 秒租约。租约过期可重新读取，不恢复任何平台写尝试。

研究、互动和回复审核必须提交对应证据。未经验证的产品推荐和链接会被阻止；非产品答疑不依赖产品验收。新入群与发送仍必须由原有显式启动的冻结任务和原生队列承担；编排租约本身无法调用平台接口或创建新的发送尝试。历史入群尝试只链接原有引用，不能重新入群。

队列存储与领取协议不代表完整业务流程已经运行。另有直接运行于 Workers 的 Telegram 执行器实现，见 [专用执行器](telegram-cloud-executor.md)。仍需本人完成独立登录，并补齐审核模型和原生任务生成编排。不要把已登记步骤数量当成已执行群数量，不要注册虚假云节点把等待状态改成运行中。

## 公开资料执行

用户后续明确要求开始执行后，可通过签名的 `POST /v1/workflow/start-public` 启用当前工作空间内的 `cloudflare-public-web`。Cloudflare 定时触发每15分钟读取一条公开搜索与两个公开 Telegram 入口，每天最多96批。`public_research` 返回实际批次、读取尝试、可用来源数及下次时间。没有打开的活动不会运行。

签名的 `POST /v1/workflow/stop-public` 只停止指定活动的公开资料轮询，保留结果和其他任务。已经发出的只读请求完成后保存结果，不再继续下一条读取；不会改动全局停止或平台尝试。

该执行器不持有 Telegram 会话，不能读取登录后的群历史、置顶或成员身份，不能入群、回复或发送私信。公开入口读取仅保存部分证据并延后完整核验，不会将研究或互动判为通过。验证码/HTTP失败留存不可用状态，不绕过验证。搜索观察到的新入口只产生待核验步骤。

公开资料轮询与 Telegram 云端执行器分别启用。平台动作继续等待原有受保护队列及可用的云端 Telegram 节点；公开资料轮询不会自动启用平台写入。
